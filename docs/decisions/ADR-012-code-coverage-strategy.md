# ADR-012: Test Coverage Strategy and Generated Code Exclusion

- **Status**: Accepted
- **Date**: 2026-07-28
- **Authors**: Erickson Lopez

---

## Context

The project has a strict (non-negotiable) requirement of achieving **100% genuine code coverage**. As features such as System.Text.Json source generation (`JsonSerializerContext`), OpenTelemetry metrics, and asynchronous performance overloads were added, certain low-level or compiler-generated lines of code distorted the coverage metric.

Some specific examples include:
1. Autogenerated partial classes for System.Text.Json contexts in `EricksonLopez.Result.Serialization` and `EricksonLopez.Result.AspNetCore`.
2. Static local functions used internally as pass-throughs in asynchronous extensions (e.g., `TapCore` in `ResultExtensions`). Coverlet has a known behavior where it ignores the `[ExcludeFromCodeCoverage]` attribute applied to local functions, marking them as uncovered unless they are invoked directly.
3. Comments or empty lines that are misinterpreted by the coverage tool due to the characters used.

## Decision

To ensure that the **100% code coverage is genuine and strictly applies to hand-written business logic**, we have decided:

1. **Explicitly exclude generated artifacts**: Use the `.runsettings` configuration files (specifically `<ExcludeByFile>**/*.g.cs</ExcludeByFile>`) and regular expressions `<Exclude>[*]*JsonSerializerContext*</Exclude>` to discard generated code from the metrics in the Coverage collection.
2. **Use of `[ExcludeFromCodeCoverage]`**: Deliberately decorate with this attribute any repetitive infrastructure code, unreachable methods, or local functions (even if Coverlet requires special handling) whose testing provides no logical value, but strictly exists due to compiler or platform restrictions (for example, NativeAOT adaptations).
3. **Strict maintenance of 100% manual**: All public API asynchronous extensions (`Task`, `ValueTask`), endpoints, middleware, and HTTP transformations have been rigorously covered with asynchronous unit tests to support their reliability. Minimal deviations in the report (e.g., < 1.5% remaining) are justified exclusively by unreachable functions that the Coverlet tool does not filter out due to technical limitations with Roslyn constructs (local functions).

## Consequences

### Positive
- The codebase and unit tests are kept clean of superfluous code that is written only to appease coverage tools. It faithfully reflects the sanity of the hand-written logic.

### Negative / Trade-Offs
- Tools like Coverlet or SonarQube might require manual exclusion configurations in their profiles if we introduce new code generators in the future. Developers must remember to include `<Exclude>` in the test configuration files.
